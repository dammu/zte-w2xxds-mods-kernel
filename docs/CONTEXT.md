# CONTEXT — W2xxDS 固件与内核机制

这里只放"换内核要知道的事实"，都是在 W203DS（固件 20251013）上实测或从源码核对过的。本机专属的数据（备份位置、资料名、路径）不在这里。

## 1. 分区与启动

- A/B 设备，`slot-count: 2`，日常只用 `_a`。`_b` 槽的 vbmeta / dtbo / vendor_boot / uboot 等与 `_a` 内容相同，但 **`bootctl is-slot-bootable 1` 返回不可启动**，所以 `boot_a` 起不来时 bootloader 不会自动回退，只能进 BROM（电源 + 音量减，出现 COM 口）用 `spd_dump` 单独写回 `boot_a`。
- 没有独立 recovery 分区，recovery 也用 `boot_a` 的内核。
- `boot_a`：Android boot header **v4**，64 MiB，页 4096。kernel 是**未压缩的 arm64 Image**（原厂 39,535,104 B），ramdisk 是 lz4，没有 dtb（dtb 在 `dtb`/`vendor_boot` 分区）。`init_boot`（8 MiB）另存第一阶段 ramdisk，`vendor_boot`（100 MiB，VNDRBOOT v4）里有 vendor ramdisk 和 167 个 .ko。
- `boot_a` 分区的 payload 后面紧跟一个 `AVB0` vbmeta 块（2304 B），分区末尾 64 B 是 `AVBf` footer。设备已解锁（`ro.boot.verifiedbootstate=orange`，`vbmeta.device_state=unlocked`），换内核不需要重签：APatch 的做法就是只把 vbmeta 块搬到新 payload 之后、改 footer 里的 `original_image_size`/`vbmeta_offset`，hash 不再匹配但解锁态 bootloader 放行。`scripts/pack_boot.py` 照此复刻，ramdisk、头部其余字段、vbmeta 块逐字节不变。

## 2. 内核与模块 ABI

- 原厂内核：`5.4.276-android12-9-gb4a927d994a0 #1 SMP PREEMPT Mon Oct 13 22:29:43 CST 2025`，Android clang 12.0.5 `r416183b`（build 7284624），LLD 12.0.5。ACK `android12-5.4` 底子，Full LTO + CFI + Shadow Call Stack，`KALLSYMS_ALL=y`，`IKCONFIG_PROC=y`（`/proc/config.gz` 可读）。
- 模块：203 个在运行时加载；147 个在 `/vendor/lib/modules`（`modules.load` 143 行），其余来自 `vendor_boot` ramdisk。全部预编译、`MODVERSIONS=y`、`MODULE_SIG_FORCE=y`，vermagic `5.4.276-android12-9-gb4a927d994a0 SMP preempt mod_unload modversions aarch64`。
- 新内核要让它们继续加载，要满足三件事：
  1. **CRC 闭合**：模块 `__versions` 段里引用的每个符号的 CRC 必须等于新内核 `Module.symvers` 里的值。205 个模块共引用 2209 个不同符号（`abi/oem-symbols-20251013.json`），其中 73 个由其它原厂模块提供。`module_layout` 的 CRC 是 `0x2f279e7b`，它覆盖了几乎所有核心结构体，是最敏感的一项。有 CRC 时内核的 `same_magic()` 不比较版本串本身，只比较后面的标志位。
  2. **签名**：每个 .ko 带 PKCS#7 签名，签名者 `CN=Build time autogenerated kernel key`。这张证书嵌在原厂 kernel Image 里（`scripts/extract_oem_cert.py` 能提出来），放进 `CONFIG_SYSTEM_TRUSTED_KEYS` 即可，新内核自己生成的 `signing_key.pem` 只签自己编的模块。另外两张嵌入的证书（`wens`、`sforshee`）是 wireless regdb 的，无关。
  3. **结构体布局**：任何改 `task_struct`、`user_struct`、`struct net` 等布局的选项都会改 CRC。ACK 5.4 里这些结构体留有 `ANDROID_KABI_RESERVE` 槽位，新增字段用 `ANDROID_KABI_USE` 放进槽位，genksyms 看到的仍是预留字段，CRC 不变。Droidspaces 的两个 kABI 补丁就是这么做的。另一种情况是字段只出现在模块看不到的私有结构体里：`CFS_BANDWIDTH` 只改 `kernel/sched/sched.h` 里的 `cfs_rq` / `cfs_bandwidth`，原厂模块不导入 `runqueues`、`root_task_group` 或任何调度 vendor hook，所以把这两段 `#ifdef` 改成 `#if defined(CONFIG_CFS_BANDWIDTH) && !defined(__GENKSYMS__)` 后 CRC 不变、模块也不会读错布局（补丁 0006）。`CGROUP_PIDS` 不行：它让 `css_set` / `cgroup` 里的 `subsys[]` 数组变长，后面字段的偏移全移，`module_layout` 也变，实测 205 个模块全部拒载。
- ZTE 开源树（Ssrml 镜像）与 W200DS 工程公开的树只差 SukiSU/SUSFS 集成的 41 个文件，是同一份 drop。它缺两样东西：`CONFIG_EXTRA_FIRMWARE` 列出的 5 个触摸固件（cts ×1、himax ×4，可用 `scripts/carve_builtin_fw.py` 从原厂 Image 的 `.builtin_fw` 表切出），以及 focaltech 升级固件数组 `include/firmware/fw_sample.i`（原厂 `zte_tpd.ko` 里对应数组在 `.bss`，即为空，放一个空文件即可）。本机触摸是 himax（spi1.0），focaltech 驱动不会被 probe。
- 原厂 config 里有 3 个 drop 中没有的 Kconfig 符号（`ZTE_CONTROL_I2C0_PULL_STATUS`、`ZTE_CONTROL_I2C8_PULL_STATUS`、`ZTE_HALL_CTL_KEYBOARD_EN`），`olddefconfig` 会丢掉，对 CRC 无影响。
- 把 `KBUILD_BUILD_USER=zte`、`KBUILD_BUILD_HOST=ironic-r5300-b0113-04`、`KBUILD_BUILD_TIMESTAMP="Mon Oct 13 22:29:43 CST 2025"`、`KBUILD_BUILD_VERSION=1`、`.scmversion=-android12-9-gb4a927d994a0` 都对上后，`uname -a` 与原厂逐字相同。

## 3. VINTF：system_server 的开机自检

- Treble 设备上 `Build.isBuildConsistent()` 就是 `VintfObject.verifyWithoutAvb()`，它读 `/proc/config.gz` 对照 `/system/etc/vintf/compatibility_matrix.<level>.xml` 里 `<kernel version="5.4.x" level="N">` 的 `<config>` 要求。不满足就每次开机弹"你的设备内部出现了问题，请联系您的设备制造商"（功能不受影响）。
- 本机 vendor manifest `target-level="7"`，但实际对 5.4 内核生效的是 **level 6** 的块（`compatibility_matrix.6.xml`，`kernel version="5.4.86"`，254 + 13 项）：用它对原厂 config 是 0 违规，用 level 5 对原厂会误报 VHOST/DEBUG_FS。`scripts/audit_vintf_kernel.py` 复现这套逻辑（矩阵文件从设备拉取），构建脚本把它做成门禁。
- 矩阵要求为 `n` 而容易被想打开的：`CONFIG_SYSVIPC`、`CONFIG_IP6_NF_NAT`。
- `/proc/config.gz` 还是这项自检的输入，所以不能靠关掉 `IKCONFIG_PROC` 来隐藏 `CONFIG_KSU=y`。它的 SELinux 标签是 `config_gz`，`untrusted_app` 域读它是 Permission denied，shell 和系统域能读。

## 4. BakaSU、SUSFS、元模块

- BakaSU 三种 hook：tracepoint（只支持 GKI2 5.10+）、手动 hook（3.4+，必须内置）、SUSFS inline hook。5.4 非 GKI 只能后两种。上游 main 在这棵树上直接可编，不需要第三方的 5.4 胶水分支。
- 上游 BakaSU 对手动 hook 的要求见 `kernel/tools/manual_hook_check.mk`，对 SUSFS 模式的要求见 `tools/inline_hook_check.mk`（七个 `ksu_handle_*` 必须在，文件里不得残留 `CONFIG_KSU_MANUAL_HOOK` 守卫）。与旧文档不同的两处：`ksu_handle_sys_read(fd, &buf, &count)` 三参数；`ksu_handle_post_execve` 只声明不定义，要调 `ksu_handle_post_execveat`。
- 管理器与内核的 uapi 版本必须一致（管理器显示 `35252/6` 这种"版本码/uapi"）；不一致会提示"需要更新管理器/内核"。管理器签名证书必须在内核 `manager/manager_sign.h` 的列表里（BakaSU、官方 KernelSU、KOWX712 三把）；CI 的 PR 构建用的是别的证书，不能用。
- ksud 不是刷内核就有：**第一次打开管理器时**才被装到 `/data/adb/ksud`，之后开机由内核注入的 init.rc 钩子启动。所以换内核后的第一次开机没有模块挂载，再重启一次才全起来。
- BakaSU 没有内置的模块挂载器，`/system` 修改靠**元模块**（`/data/adb/metamodule` 软链，一次只能有一个）。Mountify 在这台机器上从 APatch 时代沿用，ksud 直接接管。`TMPFS_XATTR` 打开后它可以走 tmpfs 后端。
- SUSFS 的持久化配置由 ksud 自带（`ksud susfs config …`，存在 `/data/adb/ksu/.susfs.json`，开机 post-fs-data 下发），管理器的 SUSFS 页面编辑同一份；不需要 susfs4ksu-module。布尔项 `add` = 开、`remove` = 关。2.3.0 的 sus_mount 是自动的：ksu 域进程做的 mount 得到 2000000000 起的假 mnt_id，`hide_sus_mnts_for_non_su_procs` 开着时非 su 进程看不到这些条目。
- `/proc/kallsyms` 里的 KSU/SUSFS 符号被 `HIDE_KSU_SUSFS_SYMBOLS` 隐藏；`/proc/config.gz` 里的 `CONFIG_KSU*` 不被隐藏（见 §3）。

## 5. Droidspaces

- 它的 `check` 探测运行中的内核，不读配置。5.4 内核按它文档的"GKI 5.4+"一节：必需 `SYSVIPC`、`POSIX_MQUEUE`、`IPC_NS`、`PID_NS`、`DEVTMPFS`、`NETFILTER_XT_MATCH_ADDRTYPE`，并要求打它的两个 kABI 补丁。本项目因 VINTF 把 `SYSVIPC` 关掉，`IPC_NS` 由 `POSIX_MQUEUE` 撑起，`check` 的必需项仍全过。
- NAT 模式容器由 Droidspaces 自己配 bridge（`ds-br0` 172.28.0.1/16）、veth、MASQUERADE、FORWARD、策略路由；容器内 IP 由**容器里的 DHCP 客户端**向它内置的 AF_PACKET DHCP 服务器申请，所以 rootfs 必须开机跑 DHCP 客户端（Alpine minirootfs 不会，手动 `udhcpc -i eth0` 即通）。
- 它的 app 向导会装一个 KSU 模块 `droidspaces`：`sepolicy.rule` 新建 permissive 域 `droidspacesd`，守护进程和容器进程都跑在这个域。SUSFS 把该域当非 su 进程：守护进程看不到 KSU 的挂载，但容器自己的挂载不会被打 sus 标记，容器正常。CLI 直接起容器时进程在 `u:r:ksu:s0`，结论相同。

## 6. 设备侧的小坑

- 重启后 USB 常退回 MIDI-only，adb 消失，需在设备上把 USB 用途切回文件传输。
- `adb install` 不带 `--user 0` 会装进所有用户资料。
- `pm uninstall --user` 等包操作一次一个，批量操作曾伴随 system_server 看门狗重启。
